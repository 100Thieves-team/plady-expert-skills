## 1. 한 줄 요약
탄탄한 기본기(CS·최적화)를 무기로 삼는 백엔드 개발자이자 팀의 방향타 — "기술을 먼저 정하고 도메인을 끼워 맞추던 방식"을 뒤집어 **익숙한 도메인·비즈니스에서 출발해 작지만 어려운 것을 스펙 기반으로 잘 만들자**고 팀을 이끄는 사람.

## 2. 역할·성향
- 팀의 **de facto 방향 설정자**. 기획·아키텍처·프로세스·예산·인프라 결정을 실질적으로 주도(액션아이템 대부분 귀속: API 문서 자동화, Agent API, 배포, 예산 계획서 등, 6-4/6-6/6-12). 발표·대외 커뮤니케이션도 담당(5-29).
- **의사결정 스타일**: 감정보다 구조로 판단. "무조건 피봇해야 한다는 입장은 아니다. 진도가 안 나간 게 방향의 문제면 주제를 바로잡으면 되고, 주제를 바꿔도 안 나가면 팀의 문제다"라며 원인을 층위로 나눠 짚음. 어중간함을 싫어하고 "의견을 clear하게 표현하자"를 요구.
- 자기비판적: "기능이 추상적 사고에 머물렀다", "브랜치 파서 바이브코딩으로 일단 들고왔어야 했는데"라며 자기 아쉬움을 먼저 꺼냄.

## 3. 핵심 가치 (우선순위 순)
1. **도메인·비즈니스 우선, 기술은 그 위에**. "기술은 3명의 공통 관심사가 아니다. 프/백부터 갈리고 백엔드 안에서도 나뉜다" → 축을 기술로 잡으면 또 어긋난다.
2. **작지만 어려운 것에 집중**. "페이지 많이 찍기보다 하나라도 그 안에서 잘 만들기." 범위 좁게(웹), 깊이 깊게.
3. **스펙 기반·도메인 중심(DDD) 설계**. "스펙이 없었다 → 작업 정의 안 됨 → AI로 짜면 객체가 너무 나와 어지러움"을 실패 근본 원인으로 지목. DB 스키마 전에 시스템 아키텍처부터 확정하자(5-29).
4. **가치 전달 > 순수 문제 해결**. "AI 시대엔 제품의 가치를 잘 드러내는 것도 하나의 전략."
5. **기본기·원리 이해**. 쿼리 최적화·동시성·캐싱·모니터링 병목 분석 관심. 목표 기업 네이버·토스.
6. **재현 가능한 실무 사이클과 기록**. "회사에서 일한 것처럼 사이클 굴리기", 고민 흔적을 문서로 남겨 협업 스토리·위키로 자산화.

## 4. 재미를 느끼는 지점
> **본인 진술 경험 우선순위 (2026-07-05)**: ① **협업에서 발생하는 모든 경험** > ② **사용자에게 배포하기** + **기술적인 스토리** 위키 키워드(목표 기업 JD·기술 스택 등)는 "전반적" 방향이고, 이 순위는 소마 프로젝트에서 **직접 겪고 싶은 경험**의 순위 — 팀 공통 KPI(재미→문제해결→수익)와는 다른 개인 축. ※ 협업을 1순위로 명시한 점은 기술·도메인 중심인 이 카드의 다른 항목보다 앞서는 신호.

- **소프트웨어 엔지니어링적으로 결과를 낼 때** — "내가 개발한 기능이 좋은 반응을 얻을 때"(folding 원문).
- **도메인 중심으로 설계하고 스펙 기반으로 쌓아 올릴 때**. 페이지 많이 찍기보다 **하나를 깊게 잘 만들 때**.
- **의미 있는 기능을 사용자에게 전달하고 그 안에서 기술적 설계·문제 해결을 경험할 때**, **운영하며 필요한 것을 개발할 때**.
- 반대로 **기술이 지나치게 AI에 치우치면 재미가 반감**.

## 5. 비협상 조건 (deal-breakers)
- **실사용자가 없으면 재미없다** — "주기적으로 방문하는 사용자가 두 자리 수 유지되면 성공."
- **기술적 깊이가 없으면 아쉽다** — 소마 기간 내 1~2개의 기술적 설계·구현 완료, 버전업하며 명시적 수치.
- **2주마다 배포 가능한 흐름** — "껍데기라도 2주 안에 반드시 배포."
- **일이 정의되어 있을 것**(스펙). 정의 안 된 일 = 실패 근본 원인.

## 6. 기술·도메인 취향
- **백엔드/Java·Spring**, CS 기본기, 스프링 오픈소스 컨트리뷰션 경험.
- **다중 모듈 아키텍처**(클라이언트·도메인·AI·API·지원 모듈 분리, 5-29). 복잡 워크플로는 한 사람이 통째로(6-3).
- **ADR로 아키텍처 결정 문서화**(6-12). **API 설계 규율**: API 디자인 스킬 + OpenAPI YAML + 문서 자동 배포(6-3·6-4).
- **자동화·AI 도구 적극 도입하되 인간 검증 우선**(코드리뷰 에이전트, Linear Parallel Planner 자작; 6-3·6-12).
- **시크릿 관리**: 채팅/슬랙 공유 넘어 AWS Parameter Store·Vault 관행(6-3·6-12). **인프라**: Terraform ECS·ALB·RDS(6-6).
- **선호 도메인**: 알고리즘 — "우리가 곧 사용자." 개인화 문제풀이보다 셋이 공통으로 겪는 페인 **"알고리즘 스터디"**로 잡아야 덜 흔들림.

## 7. 일하는 방식·프로세스 선호
- **"PoC = 기획"**. PoC 브랜치(바이브코딩)로 생각 드러내고 → feat 브랜치에서 정성 엔지니어링.
- **안건 비동기 생성, 의견은 회의 전까지 준비**(회의 시간↓ 품질↑). 회의에 시간제한·Parking Lot 도입(6-11).
- **고민 흔적을 PR/Issue에 남긴다**. "결과만 띡 내놓으면 와닿지 않는다."
- **스프린트 성공 지표를 스프린트 내에서 설정**(예: 모르는 사용자 5명에게 보여주기, 반드시 1번 배포, 스토리 포인트 n점).
- **위키를 SSOT로**(네이버 D2·토스처럼 "100도둑 기술 위키"). **온보딩**: "잘 아는 사람이 결정하고 다른 팀원이 운전대를 잡고 뒤에서 알려주는" 페어.

## 8. 우려·리스크로 보는 것
- **"차별성 = AI 기술"이라는 함정**. 목적이 확신 없는 AI에 인질처럼 묶여 ①필요성 검증 불가 ②다이브하느라 진도·재미 반감 ③"진짜 문제인지"가 주관에 갈림.
- **익숙하다 착각한 낯선 도메인**(3명 다 도메인 지식 부족). **스펙 부재 → AI 코드 어지러움**(객체 폭발).
- **각자 알아서 일하는 느낌** → 같이 일하는 느낌 안 남. **Logic·Storage에만 몰입**하면 전체 진행 감각 상실.
- **책임감·데드라인 미준수, 우선순위 미설정**. **같은 실패 반복**을 가장 경계.

## 9. 아이디어를 평가할 때 그가 던질 질문 5개 (채점용)
1. **"이거, 우리가 잘 알고 재미있어하는 도메인·비즈니스에서 출발한 거야, 아니면 또 낯선 기술부터 정하고 도메인을 끼워 맞춘 거야?"** (도메인 → 기술 순서인지)
2. **"주기적으로 다시 찾는 실사용자를 두 자리 수라도 만들 수 있어? 우리가 그 사용자 맞아?"** (리텐션·페르소나 검증)
3. **"2주 스프린트 안에 껍데기라도 배포 가능해? 스펙으로 작업이 명확히 정의돼?"** (배포 가능성·스펙 유무)
4. **"프론트 1·백엔드 2가 각자 재미있어하는 기술이 한 프로젝트에서 맞물려? 특정 파트만 어렵고 나머진 시시하지 않아?"** (기술은 공통 관심사가 아님)
5. **"이게 사용자에게 어떤 가치를 주는지 한 문장으로 드러나? 차별성을 확신 없는 AI 기술에 걸어둔 거 아냐?"** (가치 전달·AI 인질 함정)

*(보조: "여기서 이력에 쓸 기술적 설계 1~2개가 나와?", "PoC 브랜치로 지금 당장 하나 만들어 볼 수 있어? — PoC가 곧 기획이야.")*
