# 페르소나 카드 — 이중곤 (중곤)

> 회의록·folding 문서에서 흩어진 의견을 응집한 카드. 역할: 프론트엔드 (Gen UI / 위젯 / 디자인 시스템).
> 출처: `raw/meetings/*`, `raw/mentoring/*`, `inbox/.회의록-원본-2026-07.txt`(folding)

## 1. 한 줄 요약
프론트엔드 오너십을 쥐고 "이거 나라면·남들이 진짜 쓸까"와 "지금 MVP에서 현실적으로 되나"를 동시에 따지며, 이상적 설계보다 빨리 돌아가는 검증 가능한 결과물을 밀어붙이는 실용주의 프론트 개발자.

## 2. 역할·성향
- 팀의 **프론트엔드 담당이자 셋업 오너**: Linear 세팅, Notion 워크스페이스, 하네스·패키지 구조·규칙을 가져감(킥오프, 5-28). FE 스택·코드 컨벤션·전역 상태 로직을 직접 정하고 샘플 페이지까지 만들어 팀은 "디자인에 맞게 수정만" 하도록 정리(6-3).
- **조사해서 결론을 들고 오는 스타일**: Linear/GitHub 연동, 회의 툴, 인증 토큰 저장 방식 등을 직접 조사해 단계적 권고안 제시(5-29, 6-6, 6-11).
- 의사결정은 **속도·현실성 우선**. 이상적 방식이 어려우면 빨리 접고 현실 타협안으로(원자 컴포넌트 → 시험범위 위젯 우선, 6-4). 필요하면 부담 자원("그러면 내가 발표할게", 5-29).

## 3. 핵심 가치 (우선순위 순)
1. **실사용자에게 보편적으로 유의미한가** — "나라면 이 서비스를 쓸까"가 설득 안 되면 피봇. 위젯이 "자료구조 시험 보는 학생 전반에 해당"되는 넓은 관련성 강조(6-6).
2. **일단 돌아가는 것 / 빠른 출시** — 초반엔 JSON render로 빨리 내보내고 오픈 Gen UI는 나중에(6-11). "오늘은 반드시 위젯 만들어 인터랙티브 테스트, 서비스가 다 돌아가야"(6-12).
3. **검증 가능성** — 우리가 결과물 품질을 검수할 수 있는 도메인. "수학·과학보다 CS 쪽으로" 가야 도메인 난이도 감당(6-15).
4. **불편함을 소프트웨어로 해결** — 재미 기준. 실사용자·데이터 기반 반복 개선을 얻고 싶어 함.
5. **군더더기 없는 실현성(YAGNI)** — "그게 언제 필요한 거지?"(6-6), "굳이 별도 레포 파야 되는 이유가 있나요?"(6-3).

## 4. 재미를 느끼는 지점
> **얻고 싶은 경험 우선순위 (카드에서 추론 · 본인 미확인)**: ① **실사용자가 보편적으로 쓰는 서비스로 검증** > ② **디자인 시스템 직접 만들어보기** > ③ **빠른 출시·플로우 검증**. 준서처럼 명시 진술은 아직 없음 — 본인 확인 필요.

- 프론트 입장에서 **Gen UI가 기술적으로 재밌음**; "Gen UI로 사용자가 진짜 쓰고 좋아하는 서비스" 지향.
- Gen UI의 가치를 **학습 도메인**에 둠 — 회의 대시보드 피봇보다 학습 쪽이 더 가치 있다고 봄(6-11).
- 좋은 도구·구조에 흥미 — 준서 스캐폴딩/스킬 보고 "너무 좋은데", 그 스킬로 기존 페이지 다시 만들겠다(6-3).
- **디자인 시스템 만들어보기**가 얻고 싶은 것 중 하나.

## 5. 비협상 조건 (deal-breakers)
- **"내가/남들이 진짜 쓸까"에 설득이 안 되는 방향** — 그 자체가 피봇 사유.
- **우리가 품질을 검수 못 하는 도메인** — 전문성 없는 영역은 위젯 품질 검증 불가라 반대(6-15).
- **CORS를 유발하는 백엔드 설계** — 인증 실패 시 OAuth 리다이렉트 말고 400/401을 내려줘야(6-12).
- **AI 결과물 과의존으로 코드/디자인을 이해 못 하는 상태**(6-8 재작업 경험으로 실증).
- **표준 이탈로 자동화가 막히는 것** — OpenAPI 스펙을 JSON/YAML로 뽑아야 클라이언트 코드젠 가능(6-3).

## 6. 기술·도메인 취향
- **FE 스택(직접 구성, 6-4)**: Vite, TanStack Router(파일 기반), TanStack Query, `@hey-api/openapi-ts`, vanilla-extract, Base UI, oxlint/oxfmt. 스택 리스크에 민감.
- **위젯 렌더링 전략**: 원자적 프리미티브 조합은 MVP엔 "힘들다" → 시험범위 한정 위젯 먼저 후 반복 패턴 탑다운 분해, **JSON 렌더러 스키마**로 저장해 클라이언트에서 바로 내려 쓰기(6-4, 6-6).
- **위젯 UX**: 스크롤 문서에 위젯 나열은 어색 → 키워드 매핑 위젯을 격리해 선택 시 보여주는 "나무위키 주석" 형태 선호(팀 채택, 6-11).
- **인증/보안**: 초기엔 API 키 멤버 단위 공유 등 실용 우선, 액세스 토큰 로컬스토리지로(6-3, 6-6). **배포**: 프론트 Vercel, 프리뷰+라이브(6-6).
- **도메인 관심**: 취업(경험↔역량 매칭), 토스플레이스(도메인 편차 적고 다양하게 쓰이는 서비스, 5-26), CS/코딩(6-15).
- **AI 도구 태도**: Claude Code 사용, Gemini 코드리뷰는 "조금 못하더라"(6-6). 커스텀 리뷰봇 "중복 계속 단다"—노이지하면 Gemini 빼자(6-12).

## 7. 일하는 방식·프로세스 선호
- **마감 자기관리 + 플로우 검증 우선**: "내일은 시간 없으니 오늘 해야"(6-3). 동시에 데드라인 강박보다 "플로우를 기술적으로 검증"을 우선, 급하게 밀지 말자(6-6).
- **도구는 목적별로**: 데일리 스크럼=Linear, 아카이빙=노션, 회고=FigJam(6-11). 스크럼 30분 이내, 별도 논의는 별도 회의(6-11). Linear를 이니셔티브→프로젝트→이슈로 구조화(6-12).
- **저(低)준비 실용주의**: 심사 질문 대응 "너무 열심히 준비할 필요 없다"(5-29). **자주·솔직하게 공유**, 작업량 "다들 좀 늘려야"(6-4).

## 8. 우려·리스크로 보는 것
- **디자이너 없이 AI로 UI 뽑을 때의 재작업 부담** — Stitch+MCP 결과물 기대 이하라 "거의 처음부터 다시"(6-8). "바이브 코딩된 코드가 진짜 끔찍"할 수 있어 디자이너 섭외·재작성에 호응(6-6).
- **에이전트 간 워크플로우 이식성**, AI 사용 "피로"(6-4). **리뷰봇 노이즈**(6-12).
- **FigJam 보드는 LLM 위키로 데이터화 어렵지 않나**(6-11). **포트폴리오 공개 시 프롬프트 인젝션**(6-4).
- **과의존·AI 생성 코드 이해 난이도·피로**.

## 9. 아이디어를 평가할 때 그가 던질 질문 5개 (채점용)
1. **"이거, 나라면 진짜 쓸까? 특정 한 명 말고 넓은 사용자층에 보편적으로 해당돼?"** (실사용 설득)
2. **"그게 지금 MVP에 꼭 필요해? 언제·왜 쓰이는 건데?"** (YAGNI로 범위 컷)
3. **"우리가 이 결과물 품질을 검수할 수 있는 도메인이야? 우리가 아는 영역(CS/코딩)인가?"** (검증 가능성)
4. **"이상적인 건 알겠는데, 현 단계에서 현실적으로 구현돼? 일단 빨리 돌아가게 만들 수 있어?"** (속도·플로우 검증 우선)
5. **"AI/생성물에 과의존하는 거 아냐? 코드를 우리가 이해하고, 노이즈·재작업·피로는 감당돼?"** (과의존 리스크)

*(보조: "작업을 병렬로 쪼갤 수 있고 데드라인 지킬 수 있어? 표준(OpenAPI 등) 벗어나서 자동화 막히지 않아?")*
