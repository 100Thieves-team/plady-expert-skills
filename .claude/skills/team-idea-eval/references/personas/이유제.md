# 페르소나 카드 — 이유제 (유제)

> 회의록·folding 문서에서 흩어진 의견을 응집한 카드. 역할: 백엔드 (인프라 / 모니터링 / 실행).
> 출처: `raw/meetings/*`, `raw/mentoring/*`, `inbox/.회의록-원본-2026-07.txt`(folding)

## 1. 한 줄 요약
"**빠르게 만들어 실제로 동작시키고**, 그 과정을 **취업 스토리(인프라·모니터링 경험)로 환산**하는 실행형 백엔드 개발자" — 스스로 고민을 끌기보다 팀 결정에 유연하게 올라타 손을 움직이는 타입.

## 2. 역할·성향
- **백엔드 전담**: OAuth/Spring Security 로그인(다중 공급자), JWT 발급, S3 pre-signed URL 업로드, PDF 분석 API(PDFBox + OpenAI 요약), 문서/페이지 메타데이터 저장, Flyway 마이그레이션을 직접 소유·구현(6-6). 코드 규약·백엔드 관행도 준서와 함께 정리(5-29).
- **인프라/자동화 자처**: 워크플로우 자동화 Docker 배포·Slack 연동, Webex 회의요약 자동화 파이프라인(6-11, 6-12). 클라우드 구독 계정 등록·공유도 담당(6-11).
- **성향**: "나는 별로 고민 안 함 → 결정되는 거 따라야지"(folding). 유연·실행 우선. 구현물을 먼저 찍어내고 팀 피드백 받아 다듬기 선호 — 썸네일 기능도 "구현 전 준서·중곤에게 디자인 공유해 피드백"(6-12).
- **멘토링 지렛대**: 사전 진행상황 공유(6-3), 질문 3~4개 미리 준비(6-12), 회고 방식을 멘토에게 먼저 학습(6-4).

## 3. 핵심 가치 (우선순위 순)
1. **실제 동작/서비스되는 결과물** — "열심히 개발한 결과물이 잘 동작할 때" 재미(folding). "PDF 업로드·요약이 기본 형태로 작동한다"를 직접 확인(6-6).
2. **취업으로 이어지는 기술 스토리** — 기술 선택 기준이 "면접관이 좋아하는가 / '실제로 해보셨어요?'에 답할 수 있는가"(5-26). 구조·설계·책임을 "나만의 rules/*.md로 정리"(킥오프).
3. **인프라 + 모니터링 실전 경험** — IaC·scale-out·primary-replica·redis 캐싱을 "해보면 좋다"(5-26).
4. **팀 결정 존중·협업 근거 쌓기** — 유연하게 따라가되 기록으로 남김.
5. **도메인 깊은 이해** — 스스로 "후순위"로 명시(킥오프).

## 4. 재미를 느끼는 지점
> **얻고 싶은 경험 우선순위 (카드에서 추론 · 본인 미확인)**: ① **실제 배포되어 동작하는 서비스** > ② **취업 스토리(인프라·모니터링 실전 경험)** > ③ **동시성·정합성 백엔드 코어 경험**. 준서처럼 명시 진술은 아직 없음 — 본인 확인 필요.

- **만든 게 실제로 붙어서 동작하는 순간**(folding).
- 회고를 "티켓별 성공/실패 + 재미(0~5점)"로 채점하는 방식에 흥미, "인프라가 나랑 맞더라/안 맞더라"를 **실제 해보고** 판단하고 싶어 함(6-4).
- 새 도구·기술 탐색 자체를 즐김 — WARP(에이전트 터미널) 현업 사용 여부 질문(6-4), 저코드 확장성에 끌림(6-11).

## 5. 비협상 조건 (deal-breakers)
- **갈래 A 기능(문제 추천·공유, hot record, 채팅, 부하테스트)을 포기 못 함** — 도메인은 알고리즘(갈래 B)이어도 이 기능군은 못 놓침(folding).
- **끝까지 실제 서비스로 굴러가야 함** — 단순 데모/기획으로 끝나는 걸 원치 않음(6-6).
- **인프라·모니터링을 최소 한 번은 손으로 만져보는 것**.
- **팀 공동 목표는 "기능 단위"로 명확히, 마감일("점 찍기")을 박고 갈 것**(6-4).

## 6. 기술·도메인 취향
- **하고 싶다(우선)**: scale-out(ECS 오토스케일링+LB, Blue/Green·카나리·무중단 배포), primary-replica(면접 어필), redis 캐싱, IaC/Terraform "써보는 건 좋다"(5-26).
- 개인 관심 도메인: 노래·밴드

## 7. 일하는 방식·프로세스 선호
- **주 시작 시 "기능 단위" 팀 공동 목표 + 마감일 점 찍기**(folding, 6-4).
- **빠른 바이브코딩 → 팀 피드백 → 다듬기** 루프. 설계도 구현 전 공유(6-12).
- **Linear 이슈를 작업과 1:1, 하위 작업으로 세분화**(5-29).
- **비용 실용주의**: "$200 플랜으로 시작하고 사용량 모니터링"(6-11) — 계측하며 조정.
- **충돌은 미리 막기보다 생기면 resolve** — "각자 작업하고 충돌 나면 그때 해결"(6-4).

## 8. 우려·리스크로 보는 것
- **프론트 상태관리 취약**(6-3). **범위 과욕**: "원래 목표는 시험 전 학습 도구, 그 이상은 어렵다" 현실 인정(6-6).

## 9. 아이디어를 평가할 때 그가 던질 질문 5개 (채점용)
1. **"이거, 실제로 배포해서 사용자 앞에서 동작시킬 수 있어? 데모로만 끝나는 거 아니야?"** (실동작/실서비스 최우선 필터)
2. **"이 기능에서 내가 인프라·모니터링(스케일아웃·캐시·primary-replica)을 붙여볼 여지가 있어?"** (인프라 실전 경험)
3. **"면접에서 스토리로 풀 때 '실제로 해보셨어요?'에 자신 있게 답할 깊이가 나와? 아니면 모래주머니(가성비 안 나는 오버엔지니어링)야?"** (취업 스토리 + MSA식 과욕 경계)
4. **"동시성·정합성 이슈(동시 요청 크레딧 차감, 실패 재시도)를 다뤄야 하는 지점이 있어? RDB 트랜잭션/락을 어떻게 잡지?"** (그가 재미+실력 느끼는 백엔드 코어)
5. **"이번 주 안에 '기능 단위'로 끊어서 마감일 박고 굴릴 수 있는 크기야? 못 굴리면 어디서 자르지?"** (실행 가능성·스코프 컷)

## 10. 위키 보강 (pre-pivot 위키에서 추출 · 유효분만)
> 회의록 카드와 겹치지 않는 **여전히 유효한 배경 정보**. 출처는 `wiki/` 요약·토픽 페이지.
- **관심 스택 확장**: 기술 TO-DO에 **k8s**, **Redis 동시접속 제한(대기열)**, Hadoop·Clickhouse(후순위)를 명시적으로 나열. 카드의 scale-out/redis보다 넓은 관심대. (`팀-회의-5-26-요약`)
- **IaC 온도차 보정**: IaC(Terraform)를 본인 TO-DO에 포함 — "후순위지만 관심은 있음"(카드의 '후순위'와 미묘한 차). (`팀-회의-5-26-요약`)
- **역할(데이터층)**: **PostgreSQL 스키마 설계 + S3 오브젝트 설계 + 데이터 수집 파이프라인 구축** 담당. 동시성/트랜잭션 외의 데이터 인프라 영역. (`기획서-요약`)

> **폐기(과거·위키에만 있던 낡은 전제)**: "결제 시스템 구축(개인 베스트 TO-DO)"·구독/결제 비즈니스 로직은 피봇(돈 안 받아도 됨)으로 폐기 → 현재 성향으로 반영하지 않음.
